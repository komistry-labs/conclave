## 1. Defect

`conclave relay import` rejected **every** provider response saved with CRLF
line endings, reporting `no-yaml-block`. Since Notepad, VS Code with default
Windows settings, and essentially every Windows editor write CRLF, and manual
relay is the only input path, the central workflow was unusable on the target
operator platform.

Discovered during post-release verification on Windows / Python 3.12:
**63 failed, 454 passed** — all 63 from this single cause.

## 2. Root cause

```python
_FENCE = re.compile(r"^[ \t]*```([^\n`]*)\n(.*?)^[ \t]*```[ \t]*$", re.S | re.M)
```

| Fence | CRLF input |
|---|---|
| opening `^[ \t]*```([^\n`]*)\n` | matches |
| closing `^[ \t]*```[ \t]*$` | **does not match** |

Under `re.MULTILINE`, `$` matches immediately before a newline. In a CRLF file
the closing line is `` ```\r\n `` — a carriage return occupies that position,
and `[ \t]*` does not match `\r`. The closing fence is never found, so no
candidate block is extracted.

The opening fence survived by accident: `[^\n`]*` captured `yaml\r`, and the
subsequent `.strip()` removed the stray carriage return.

**Not a Python 3.12 regression.** Reproduced on Python 3.10.12 on Linux. The
defect is platform-independent CRLF handling; Windows merely supplied the first
CRLF input.

## 3. Why the tests missed it

Every fixture used `Path.write_text()`, which performs newline translation.
The same test wrote LF on Linux and CRLF on Windows — so the suite exercised a
different input on each platform and nobody noticed. 517 tests passed on Linux
while the tool was inoperable on Windows.

The fixture pattern, not the assertion, was the flaw. Fixing the regex without
fixing the fixtures would have left the identical blind spot for the next
CRLF-sensitive path, so `tests/test_line_endings.py` writes **bytes** and now
carries an AST-based guard that fails if any fixture in that file calls
`write_text()`.

## 4. Fix

`handoff.py` — one new function, one line added to `extract_yaml_block`:

```python
def normalise_line_endings(text: str) -> str:
    return text.replace("\r\n", "\n").replace("\r", "\n")
```

Applied to the working copy at the top of `extract_yaml_block`.

**Normalisation was chosen over a CR-tolerant pattern** because it also keeps
carriage returns out of the extracted block. A Windows-authored reply and a
Linux-authored one now produce byte-identical Handoff Packets, differing only
in `raw_response_hash` — which *should* differ, because the bytes genuinely did.

Normalisation runs on an in-memory string, after raw preservation and after
strict UTF-8 decoding. It cannot reach the evidentiary artifact.

## 5. Regex audit — newline sensitivity

Every regex in the codebase, classified as instructed.

| Regex | Consumes | `re.M` | Class | Reachable with CR? |
|---|---|---|---|---|
| `handoff._FENCE` | **provider-authored response text** | yes | **newline-sensitive** | **yes — this was the defect** |
| `models.TASK_ID_PATTERN` | `task_id` field of a Task Packet | no | newline-sensitive | **no** — see below |
| `taskpacket._SLUG_STRIP` | operator CLI objective string | no | newline-insensitive | n/a |

**`TASK_ID_PATTERN` was investigated and deliberately not changed.** It is
technically newline-sensitive — `$` in a non-multiline pattern matches before a
trailing newline but not before a `\r` — but a carriage return cannot reach it:

- `task_id` is not a provider-supplied field; the handoff schema does not
  contain it
- the only route is a YAML document, and YAML consumes the line break as
  document structure rather than scalar content: a CRLF-authored packet yields
  `'TP-draft-abc-0123456789'`, identical to LF
- the JSON route would require an explicitly escaped `\r`
- `task_id` is generated by CONCLAVE and validated only on packets CONCLAVE wrote

Verdict: **theoretically sensitive, not reachable. No repair warranted.** Per
instruction, scope was not broadened into speculative refactoring.

Non-regex parsers consuming externally-authored text were also checked:
`yaml.safe_load`, `json.loads` and `str.splitlines()` are all newline-
insensitive. `hash_bytes(binary=True)` is byte-exact **by design** — CRLF is
evidence there, not noise, and was left alone.

**Beyond `_FENCE`, no additional CRLF-sensitive parser was found.**

## 8. Windows smoke workflow

Full workflow run against a reply written with **explicit CRLF bytes**
(28 CRLF endings, 0 bare LF):

```
init            ok
ledger init     ok
task create     ok
relay export    ok
relay import    IMPORTED          <- was: REJECTED no-yaml-block
scope review    within_scope
council review  ready_for_human_review
ledger verify   chain verified, 8 entries
```

Evidence checks on the resulting artifacts:

```
raw artifact    : 28 CRLF pairs   -> byte-exact evidence preserved
stored handoff  : 0 CRLF          -> canonical LF as designed
body scalar     : 'first line\nsecond line\n'  -> no carriage returns leaked
```

The blocker is gone, and the preservation guarantee it might have compromised
is intact.

## 10. Why release history was not rewritten

`v0.1.0` is unchanged and its tag has not moved.

Re-tagging would have erased the most useful thing that has happened since the
release. The v0.1.0 notes explicitly listed "no Windows execution" as a
verification gap; that gap then produced exactly the class of defect it warned
about. The sequence — released, verified, defect found, patched — is a true
record of how the software was developed, and it is worth more than a tidy
history in which the defect never appears.

A reader of `v0.1.0` should be able to see that it carried this blocker. That
is what a patch release is for.

## 11. Compatibility

**Fully backward compatible.** No schema version changed.

- `task-packet/0.1.0`, `handoff-packet/0.1.0`, `scope-review/0.1.0`,
  `council-review/0.1.0`, `conclave-ledger/0.1.0` — all unchanged
- every artifact produced by v0.1.0 is read, verified and hashed identically
- every hash computed under v0.1.0 is reproduced exactly under v0.1.1
- no migration required; existing workspaces continue to work
- v0.1.1 accepts strictly **more** input than v0.1.0: replies that previously
  failed now import. Nothing that v0.1.0 accepted is now rejected.
